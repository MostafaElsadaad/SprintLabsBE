# Lobby mission integration
Implement the mission screen using GET `/api/v1/Missions/me` after authentication and on lobby return. Group by Weekly/Monthly/Open and category; display title, description, progress/target, remaining UTC expiry, status and configured rewards. Count bar clamps to target; show claim only for Completed. Mark current-period Claimed missions as collected. Expired/ended periods are omitted. Loading skeleton, empty active-missions state and retryable error state must be distinct.
Claim sends POST `/Missions/{playerMissionId}/claim` with no body. Disable the button while pending; update mission status and show returned XP/coins/item reward. Claims are safe to retry after a lost response. Claim-all sends POST `/Missions/claim-all`; empty list means nothing was claimable. Display immediate box item feedback; there is no unopened box inventory. Refresh `/Progression/me` after claims/mission load to show balances including lazy auto-claims. Replayed claim balances are the original snapshot.
Never send mission events from the game client or place server credentials in client settings. Mirror emits events from validated server actions only, resolves authenticated human member identity, omits bots/AI control, keeps per-occurrence event IDs across retries and sends events chronologically. The response includes updated/completed mission entries for an owning-player notification. This feature does not change Unity/Mirror gameplay or the lobby UI; NOX-118/119 integration remains separate.
Admin configuration endpoints use a platform admin account, never community owner/teacher privileges. Template form fields: missionKey/title/description/category/period/event/progress/target, conditions as validated scalar map, progressField, resetEventType, matchScoped, repeatValue and XP/Coins/Box rewards. Activation form: name, period, UTC start/end (no end for Open), fixed/pool items, weights/order, random count and auto-claim checkbox. Validate bounds in api.md, handle 400 field correction/409 conflicts/503 retry. Configuration returns numeric created IDs. Template preview supplies full definitions; at most 100 entries. Existing backend has no shop UI or box management APIs; catalog provisioning is a deployment/admin-data prerequisite, with explicit demo seed examples for development.
No dashboard pages, mission sorting/filter implementation, admin mutation screen, daily missions, mobile push or unopened boxes are added here. Optional management CRUD is documented as deferred rather than implying unavailable endpoints exist.
# Weekly/seasonal game UI — 2026-10-23 extension

Unity feature 010 wires the existing mission panel/card assets to Weekly, Seasonal and History. The common authenticated profile store owns current/history rows, loading/error state and claim intents; the Bootstrap root owns HTTP composition/session cancellation. UI makes no HTTP calls and never supplies completed mission facts.

Load GET `/Missions/me` after authentication, on opening/refreshing the mission panel and after synchronized match rewards. Filter current cards by Weekly/Seasonal. Card fields: title, progress/target, XP, coins and backend status; Claim is enabled only for Completed and disabled during requests. Claim POST `/Missions/{playerMissionId}/claim`, refresh missions and persisted profile values; do not calculate rewards locally. Refresh profile after current-mission load because expiry may auto-claim. Display loading, empty and retryable error states separately. Clear all rows and ignore stale callbacks on logout/account change.

History calls GET `/Missions/me/history?page=N&pageSize=30`; show completed/claimed entries, saved reward amounts and completion/claim date, with Previous/Next navigation. History does not grant anything and has no claim button; current claimable missions remain on their active board. No historical screen is implied for incomplete expired missions.

Admin game provisioning uses POST `/admin/missions/seed/game`, not the demo seed. Future periods beyond current/next require another explicit seed or future scheduling work. No external scheduler or new admin frontend is added. Existing Monthly/Open content and old API contracts remain supported by the backend but are not shown on the new Weekly/Seasonal player boards.
